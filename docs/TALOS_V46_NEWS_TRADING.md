# TALOS v4.6.0 — كتالوج استراتيجية تداول الأخبار

**تاريخ الإصدار:** 10 أكتوبر 2026  
**المنصة المستهدفة:** React / FastAPI / PostgreSQL (Neon) / Render / Telegram / CCXT  
**حالة التنفيذ:** البحوث ومعاينة الأخبار والتداول الورقي موجودة في هذه الحزمة، والتداول الحقيقي التلقائي غير مفعّل وغير متاح في مسار أخبار Talos الجديد.

## 1. ما الذي تغير؟

- يظهر شريط **Operations** في جميع الصفحات، ويطلب حالات المهمات من PostgreSQL كل ثلاث ثوانٍ تقريبًا أثناء فتح الموقع. يعرض المرحلة، النسبة المسجلة في قاعدة البيانات، المحاولات والخطأ، مع توضيح حالة عامل المهام.
- عند إعادة فتح **Telegram Replay** يسترجع أحدث مهمة مطابقة للمصدر، وتستمر المهمة على السيرفر بعد تغيير الصفحة. النسبة **مرحلية** وليست تقديرًا زمنيًا؛ وإذا بقيت 0% فالعمل ربما لم يبدأ أو لم ينه أول دفعة.
- تعرض **Source errors** قائمة المصادر التي فشلت مع رسالة `last_error` وتاريخ آخر نجاح. لا يمكن تحديد أسباب الثمانية أخطاء من صورة الرقم وحدها.
- يوجد زر **Make a trade · review** أسفل كل خبر في Dashboard وIntelligence، يفحص الحدث الأصلي وأهلية التداول وبيانات السوق العامة.
- صفحة **News Strategy** تتيح تعديل إعدادات التداول الورقي بعد تسجيل دخول Admin، واستعراض صفقات الأخبار ونتائج Paper بمعزل عن Live.
- يُرسل البوت إشعارات للأخبار المختارة، والتداولات الورقية المنفذة، وإغلاقات الورقي. يمكن تفعيل أمر `/paper EVENT_ID` **في المحادثة الخاصة المحفوظة فقط**.

## 2. من الخبر إلى قرار التداول

1. يُسجّل Talos أول وقت رصد للخبر `first_seen_at`، ووقت النشر إن توفر `published_at`. لا تُستخدم النسخ المعدّلة اللاحقة في استنتاج قرار أصلي بأثر رجعي.
2. يأخذ **التصنيف** نوع الحدث وأهميته وموثوقية مصدره. درجة الأهمية ليست احتمال نجاح صفقة.
3. **فلتر التداول التلقائي الورقي الحالي شديد التحفظ:** أخبار إدراج عملات Spot الواضحة فقط مع رمز عملة مدعوم مقابل USDT. أخبار الاقتصاد الكلي والأسهم والأحداث غير الواضحة والحذف أو الاختراق تُعرض للبحث ولا تؤدي لشراء تلقائي.
4. يُرفض الخبر إذا تجاوز زمن اكتشافه بعد النشر أو عمره بعد الرصد الحد المحدد، أو إذا كان زمن نشره مجهولًا، أو إذا غابت النسخة الأولى.
5. يُطلب سعر `bid / ask / last` من البورصة المختارة، ويُفحص السبريد وعمر توقيت السعر وتوفر الزوج. غياب سعر قابل للتحقق يوقف الدخول.
6. إذا نجحت الفحوصات وكان Auto Paper مفعّلًا، تُنفّذ **صفقة ورقية فقط** مرة واحدة لكل حدث، ضمن ميزانية ومخاطر وحظر التكرار وفترة التهدئة.
7. تراقب خدمة ورقية بالخلفية شروط Stop / Target / Max Holding بفاصل تقريبي 60 ثانية، وليست أوامر وقف فعلية في البورصة. قد تتجاوز الأسعار المستويات قبل المراجعة.

## 3. متغيرات الاستراتيجية الأساسية

| المتغير | القيمة الافتراضية | الوظيفة |
|---|---:|---|
| `auto_paper` | false | الشراء الورقي التلقائي بعد قبول كل الفلاتر |
| `auto_live` | false — مقفل | ليس هناك شراء تلقائي بأموال حقيقية في وحدة الأخبار الجديدة |
| `broker_id` | binance | بورصة البحث وتنفيذ المحاكاة الورقية |
| `quote_currency` | USDT | عملة التسعير المدعومة حاليًا |
| `quote_amount` | 50 USDT | مبلغ شراء ورقي واحد |
| `max_position_fraction` | 0.005 = 0.5% | الحد الأقصى لحجم مركز واحد من Equity الورقي |
| `max_news_exposure_fraction` | 0.02 = 2% | سقف إجمالي مراكز الأخبار الورقية المفتوحة |
| `min_importance` | 75/100 | الحد الأدنى لأهمية الخبر التحريرية |
| `min_reliability` | 0.8 | الحد الأدنى لموثوقية المصدر في قاعدة البيانات |
| `max_detect_lag_sec` | 90 ثانية | أقصى فرق بين وقت نشر الخبر وأول رصد، إن توفر وقت النشر |
| `max_news_age_sec` | 90 ثانية | أقصى عمر من أول رصد حتى معاينة الدخول |
| `max_spread_bps` | 15 bps | رفض سبريد أوسع من الحد؛ 1bp = 0.01% |
| `max_slippage_bps` | 8 bps | الانزلاق **المفترض في المحاكاة لكل جانب**؛ ليس ضمانًا لسعر سوق حقيقي |
| `fee_bps` | 10 bps | رسوم تداول مفترضة لكل جانب |
| `stop_loss_pct` | 1.0% | شرط خروج ورقي بعد انخفاض السعر |
| `take_profit_pct` | 1.8% | شرط خروج ورقي عند صعود السعر |
| `max_holding_minutes` | 30 دقيقة | الإغلاق الورقي بعد نهاية الوقت المحدد |
| `max_daily_entries` | 3 | العدد الأقصى لعمليات الدخول الورقية في اليوم |
| `cooldown_minutes` | 30 دقيقة | منع إعادة دخول رمز معين خلال فترة التهدئة |
| `max_daily_loss_pct` | 1% | إيقاف مراكز أخبار جديدة بعد تجاوز الخسائر المحققة لليوم بالنسبة إلى Equity |

**حساب تقريبي:** رسوم طرفين (10 + 10) bps، وانزلاق طرفين (8 + 8) bps = 36 bps تقريبًا أو **0.36%** فوق حركة السعر، بالإضافة إلى أثر السبريد وطريقة التسعير وفرق وقت التنفيذ. تغير سعر البيع الفعلي قد يزيد الخسارة. مبلغ 50 USDT وتوقف 1% يعني حركة سوق تعادل 0.50 USDT قبل التكاليف؛ ليس مخاطرة كلية مضمونة.

## 4. طريقة حساب «فرصة فاتت»

- يقارن Replay للخبر أول شمعة دقيقة واحدة بعد وقت الرصد بحركة الشموع التي تلتها، ويعرض `MFE` (أكبر ارتفاع مرصود) و`MAE` (أكبر انخفاض مرصود)، مع تكاليف مفترضة.
- مثال توضيحي فقط: صعود أعلى شمعة +3.0% خلال خمس دقائق، وتكاليف افتراضية 0.36% يعطي **+2.64% بالقمة الحسابية**. هذا ليس عائدًا محققًا، ولا يثبت إمكانية البيع عند القمة أو سبب الحركة.
- إذا لم توجد شموع مناسبة أو لم تتوفر البورصة، يكتب النظام `No candle data` أو سبب الرفض ولا يصنع رسمًا مزيفًا.
- **مصدر 1m OHLCV غير كافٍ لحسم صفقة News scalping بالثواني.** يحتاج ذلك تسجيل quotes / trades / order book بالزمن الفعلي من مزود مناسب.

## 5. نسبة النجاح، والتجربة الورقية مقابل الحقيقية

- تبقى `estimated_win_probability_pct` **null**؛ ليس لدينا نموذج معاير من تاريخ أخبار/نتائج كافٍ لإعطاء نسبة نجاح مستقبلية.
- تُعرض **نسبة النجاح التاريخية للورقي** فقط بعد إغلاق 30 صفقة أخبار أو أكثر، مع حجم العينة صراحةً؛ لا تُفسر على أنها احتمال ربح قادم.
- تعرض Live عدد الأوامر الحقيقية التي يحمل سجلها `status=success`، ولا تعرض P&L مُختلقًا قبل تسوية وتنزيل النتائج والرسوم من الوسيط.
- لا تُرقّى الاستراتيجية تلقائيًا إلى تداول حقيقي. معيار المراجعة المقترح: 30 صفقة مغلقة على الأقل خلال 14 يومًا، عائد صافٍ موجب بعد التكاليف، اختبارات تأخر التنفيذ والانزلاق، تراجع أقصى مقبول، تجارب خارج العينة، وموافقة يدوية مع اختبار صغير. هذا **معيار مراجعة** وليس ضمان نجاح ولا نظام ترقية أوتوماتيكي مفعّل.

## 6. إشعارات Telegram وأوامرها

1. من Admin → Secure Vault أضف `telegram_notify` وفيه `bot_token`، ثم `chat_id` الخاص بمحادثتك **الخاصة** مع البوت.
2. لقراءة الأوامر من البوت، ضع في Render Environment: `TELEGRAM_PAPER_COMMANDS_ENABLED=true`. أعد النشر.
3. أرسل إلى البوت: `/help` لشرح الأمر، و`/paper 123` لطلب **شراء ورقي فقط** لرقم الخبر 123. يُعاد فحص عمر الخبر والسبريد والقيود عند استلام الأمر؛ قد يرفض لأن الخبر صار قديمًا أو لأن المخاطر لا تسمح.
4. النظام لا يقبل أوامر `/paper` من قروب أو Chat ID مختلف، ولا يستقبل مفاتيح API من Telegram. لا توجد أوامر `/buy-live` في وحدة أخبار Talos.
5. لا تفعّل استقبال الأوامر لبوت يستعمل polling/webhook آخر في الوقت نفسه، لتجنب التنازع على Telegram `getUpdates`.

## 7. تشخيص Replay وSource errors

- `queued` = الطلب موجود في قاعدة البيانات، ليس تقدمًا. ابدأ من `/health`: يجب أن يكون `job_worker=true` و`database=ready`، وأن تتقدم `heartbeat_at` وحالات Jobs. عند Render Free قد تنام الخدمة وتعود لاحقًا.
- إذا انتقلت لصفحة Research أو Intelligence، فوظائف الخلفية تواصل التشغيل مادام سيرفر Render نفسه يعمل. شريط Operations يقرأ تحديثاتها بصورة مستقلة.
- `8 Source errors` تعني وجود ثمانية مصدرًا لديهم `last_error`. افتح Dashboard → Source errors · details أو Intelligence → Source coverage لمعرفة HTTP 403/429 أو timeout أو تغيير شكل RSS/HTML لكل مصدر.
- بعض المصادر العامة في النسخة الحالية تُفحص كل 45-360 دقيقة تقريبًا، ودورة الجمع الأساسية كل ساعة؛ **هذا ليس مخططًا منخفض التأخر**. حتى مع تفعيل Auto Paper قد تفوت نافذة الـ90 ثانية. وضع الخدمة على خطة دائمة لا يجعل المصدر الخارجي أسرع تلقائيًا.

## 8. طريقة النشر

- الحزمة الأولى: Backend + ملفات Docker/Render الرئيسية، **99 ملفًا أو أقل**.
- الحزمة الثانية: Frontend + ملفات الواجهة، **أقل من 100 ملف**.
- فك كل ZIP وارفع **المحتويات** على دفعتين إلى **جذر المستودع نفسه**، مع الحفاظ على `backend/` و`frontend/` وملف `Dockerfile` في الجذر. لا تجعل المشروع داخل مجلد إضافي مثل `Talos-v4.6/`.
- Render: Dockerfile Path `./Dockerfile`, Docker Build Context `.`, Root Directory فارغ، Health Check `/health`. أبقِ `LIVE_TRADING_ENABLED=false` أثناء الاختبار واحتفظ بقيمة `SECRET_KEY` القديمة حتى لا تضيع إمكانية فك تشفير بيانات Vault القديمة.
- قاعدة Neon: تتكوّن تلقائيًا جدول `news_trade_decisions` عند تشغيل `create_all()` من دون حذف الجداول السابقة. يلزم فحص الترحيل ونسخة احتياطية قبل نشر أي تحديث على قاعدة إنتاجية.
- بعد النشر اختبر `/health`, `/api/public/build`, تبويب Jobs، معاينة خبر، وزر Paper في وضع آمن. لا تعتبر نجاح Unit Tests إثباتًا لاتصال Render/Neon/Telegram أو سلامة تنفيذ أوامر حقيقية.

## 9. الحدود الحالية — قائمة واضحة

| الميزة | الوضع |
|---|---|
| إظهار أسباب أخطاء المصادر | موجود بعد النشر مع بيانات Neon الفعلية |
| متابعة Jobs ومراحل Replay في جميع الصفحات | موجود، مع تقدم مرحلي بعد كل دفعة |
| تاريخ مرور الخبر وحركة شموع الدقيقة | موجود متى توفرت بيانات عامة قابلة للتحقق |
| زر Make a trade لكل خبر | موجود، مراجعة ثم ورقي يدوي |
| تداول ورقي تلقائي | متاح اختياريًا، مقفل افتراضيًا |
| إرسال إشعار إلى البوت وأمر `/paper` | متاح مع إعدادات Telegram الخاصة |
| احتمالية نجاح مستقبلية مدرّبة ومعايرة | **غير متاحة**؛ لا نخترع نسبة |
| أوامر Live تلقائية بناءً على خبر | **غير متاحة** في الاستراتيجية الجديدة؛ تتطلب مراجعة أمان منفصلة |
| أوامر وقف حقيقة في البورصة | **غير متاحة** في المحاكاة الورقية؛ مراقبة برمجية فقط |
| بيانات WebSocket وتداول بزمن أجزاء الثانية | **غير متاحة** عبر المجمع الحالي |
| ترقية تلقائية من Paper إلى Live | **غير متاحة**؛ يتطلب تحققات وموافقة يدوية |
| ربح/خسارة Live مُسوّى من البورصة | **غير متاح** حاليًا في لوحة News Strategy |

**الخلاصة:** هذه نسخة بحث تداول أخبار ورقي مدققة، وليست وعدًا بربح أو منصة HFT ولا نظام تنفيذ حقيقي تلقائي جاهز للإنتاج.
